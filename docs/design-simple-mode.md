## 1. Who is admin on a Custodia machine

### 1.1 The three options, revisited

Revised after DS1 (Alex, 2026-09-30).

| Option | What it means | Verdict |
|---|---|---|
| A. The person has no admin rights; nothing asks for a password | They live in a normal account. Root work is done by the machine itself (updates) or by a helper. | My first recommendation. Denied by Alex: it restricts. |
| B. Only a remote helper administers | A standing helper account for Alex. | Standing access contradicts "responsible for themselves"; kept only as an opt-in question (DS9). |
| C. The person is admin, every prompt in plain words, everything undoable | `wheel`, sudo with their password, polkit prompts reworded; a snapshot before every admin authentication; pause and scam cue on the destructive few. | Chosen (DS1). |

What changes my earlier objection to C. I wrote that a person who does not know what admin means will type their password into any box that asks nicely, so the prompt becomes theatre. That is still true, and the design no longer relies on the prompt. It relies on three things a scammer cannot talk past: the snapshot taken before the password is even checked (so whatever follows is undoable), the fact that the assistant and the help channel cannot be steered into destructive work (no shell tool, ID whitelist), and the pacman, systemd and polkit settings that make the destructive few slow and loud instead of one keystroke away. The prompt's job is now only to tell the truth in plain words. What the design cannot undo is listed honestly in 1.4.

### 1.2 Threat model for a Custodia machine

Revised after DS1 (Alex, 2026-09-30): TS1, TS5, TS7, TS8 and TS10 changed.

The person is not an attacker: they own the machine and can boot the rescue ISO. The model protects them from mistakes, from being talked into things, and from software that asks for more than it should.

| # | Scenario | Answer |
|---|---|---|
| TS1 | Scam call or pop-up: "open a terminal and type this" or "enter your password to fix the virus" | The assistant never shows a command and remote help only accepts Alex's RustDesk ID (section 5). The terminal exists (1.5): opening it shows a one-line warning, and every `sudo` password prompt carries the scam cue and takes a snapshot first. Damage to the system is undoable from the boot menu or by Alex; damage to their own files is undoable from the hourly home snapshot (DS12). What is not undoable: a password or a payment given away on the phone. |
| TS2 | A Flatpak asks for the whole home directory or more | Verified subset by default; the store shows what an app can reach in plain words (Venus); user-level installs cannot touch the system; new permissions from updates go into the helper's digest. |
| TS3 | An update breaks boot or the desktop | Pre-snapshot, post-update doctor, undo from the package cache, boot guard that falls back to the pre-update snapshot on its own, LTS kernel as a second entry, rescue ISO last. |
| TS4 | Remote help abused, or a session nobody sees | Click-to-accept, ID whitelist, service off unless "Get help" was pressed, banner while connected, Acta records the session, no unattended password, no SSH, no terminal or file channel in RustDesk. |
| TS5 | The assistant does harm because the person said yes | No shell tool; fixed MCP tools that are each undoable, or need the person's password with a snapshot first, or do not exist (the destructive few). |
| TS6 | Prompt injection through a web page or app description | Same as TS5: the worst outcome without the password is a Flatpak install from the verified subset or a settings change; with the password, a repo package install or a service change, snapshotted and logged. |
| TS7 | The help unlock is borrowed: a process other than Alex's screen session uses the unlocked window | The unlock covers only `invictus-sys` verbs and the administrator terminal action, for the person's user, for a bounded time; the assistant's action tools refuse to run while a help session is open; every call is logged with the session id; the unlock cannot renew itself (its own action needs the password). |
| TS8 | The person forgets their login password | Rescue screen on the Invictus USB stick resets it (DS4); the disk is not encrypted (DS8) so nothing is lost. |
| TS9 | Machine off for months, then updates | The updater refreshes `archlinux-keyring` and `invictus-keyring` first, then the rest; a keyring failure is a helper request, not a half-done update. |
| TS10 | The person, or someone at their keyboard, turns off the safety net (updates, snapshots) or removes the desktop | Not prevented, by design. Made slow and loud: `HoldPkg` confirmation for core packages, static update timers that `systemctl disable` does not touch, no permanent off switch in Settings, and the doctor and the helper digest flag it the same day. |
| TS11 | Revised (Alex, 2026-09-30, guard rails and flavors): a scammer on the phone says "go to Settings and switch Guard rails to Libertas", then continues the TS1 script on a machine with no holds and a freer assistant | The switch to Libertas is itself the most guarded action on the machine: hold, scam cue, plain warning, password, and a snapshot "Before: guard rails off" that the switch cannot skip. Settings offers "For an hour" as the first choice (DS13), so the rails come back by themselves. `invictus-doctor`, the Help panel and the helper digest say "Guard rails: Libertas since <time>" until they are back. What is lost while Libertas: the holds, the scam cue, the assistant's tiers, and its fixed tool list only if the person also switches on Full access (12.3; cleared when the rails come back); what is not lost unless the person also turns it off in Settings: the snapshot before admin actions, the boot guard, the home snapshots; never lost: the pre-switch snapshot, Acta, the help whitelist. So the scammer's script gains a faster machine, not an unrecoverable one. |
| TS12 | Revised (Alex, 2026-09-30, guard rails and flavors): a process running as the user (a bad script, an injected assistant on a Libertas machine) switches the rails to Custodia without a password, to reach the tier 1 verbs that Custodia grants without a prompt | Contained by what tier 1 contains: update from our repos, undo of that update, a snapshot, the doctor, a report collected but not sent, and "Get help" that still needs a click on screen from the whitelisted ID. None gives a process anything it could not already do as the user, and none is destructive. The switch is `YES` only for a local active session (not a cron job or a remote shell), is logged in Acta, and shows a notice on screen; it cannot switch to Libertas. |

### 1.3 Accounts and groups

Revised after DS1 (Alex, 2026-09-30): the whole section.

- Person: a normal user in `wheel` plus `input kvm audio video` as the installer gives everyone. `sudo` works with their password; `sudoers` has no NOPASSWD line for anything (design MUST A1 holds). Polkit's admin identity stays `unix-group:wheel` (Arch's `50-default.rules`, verified), so every `auth_admin` prompt asks for their own password, drawn in plain words by the Atrium shell (1.4).
- Root: locked (Calamares `setRootPassword: false`, verified in `users.conf`). There is no second password on the machine to leak or forget; `sudo -i` is root when root is needed.
- No helper account by default. If DS9 is approved, first start offers "Let Alex fix this computer when I'm not here" as an opt-in that creates the account; off by default, and the person can remove it in Settings > Help.
- Revised (Alex, 2026-09-30, guard rails and flavors): the installer installs the same packages on every machine (`invictus-guardrails`, section 6.1, is always present) and writes two values: `/etc/invictus/guardrails` (`custodia` on the plain path; the Advanced path offers `libertas`) and the first user's `~/.config/invictus/flavor` (`atrium` on the plain path; Advanced offers `tessera`). It then runs `invictus-sys guardrails apply` once so the derived files of 1.6 match. `sshd` is disabled and the stable channel set on every install. No account is created beyond the person's.
- Revised (Vulcan, 2026-10-08, sshd off means off): disabling `sshd.service` was not enough. systemd 256 and later run `systemd-ssh-generator` at every boot, and whenever `sshd` is installed it binds sshd to a local AF_UNIX socket (`/run/ssh-unix-local/socket`; also AF_VSOCK port 22 in a VM), found on the live image at the first hardware boot. The generator is masked (a link to `/dev/null` at `/etc/systemd/system-generators/systemd-ssh-generator`, the way `systemd.generator(7)` documents) on the live image (`iso/airootfs`, kept on install) and by the settings job on every install. Chosen over `systemd.ssh_auto=no` on the kernel command line: the mask also drops `systemd.ssh_listen=` and the `ssh.listen` credential, which `ssh_auto=no` still honours, and it does not depend on each boot entry's command line. Checks: `tests/iso/jobs.sh`, `tests/iso/profile.sh`, `tests/iso/e2e-jobs.sh` (real generator, control first), and the QEMU boot smoke test fails on any system socket naming ssh.
- Revised (Vulcan, 2026-10-08, pre-release, Janus I-2): the mask is now a file of the `invictus-sys` package (`pacman -Qo` names it), not something the installer writes. Every Invictus machine has `invictus-sys` (`invictus-tools`, so every desktop, depends on it), adopted installs included, which never get `invictus-base`; the live image has it through `invictus-base` -> `invictus-guardrails`. The copy in `iso/airootfs` and the settings job's write are gone: an unowned copy would make pacman refuse the package ("exists in filesystem"). The settings job now only reports whether the mask is there. Installs made from a dev ISO before this change have an unowned link, and pacman refuses the new `invictus-sys` over it ("exists in filesystem"), so every update fails. On each such machine, run this once before the first update: `sudo rm /etc/systemd/system-generators/systemd-ssh-generator`. The new updater's `--overwrite` for that one path (design.md note 56) cannot do it for them: it arrives in the update that fails (Janus PL-L1). It stays for later conflicts.
- Switching guard rails is the person's own verb (`invictus-sys guardrails set libertas|custodia`, section 1.6): to Libertas with password, hold, plain warning and snapshot; to Custodia instantly. The assistant has no tool for either direction.

### 1.4 Childproofing: the guardrails

Revised after DS1 (Alex, 2026-09-30): new section.

Each guard is marked **safeguard** (prevents damage or makes it undoable whatever the person clicks), **friction** (slows the moment down; a determined or well-coached person gets past it) or **clarity** (tells the truth; changes nothing). Against a scammer on the phone only the safeguards hold; friction and clarity work when the person reads, which is sometimes.

Revised (Alex, 2026-09-30, guard rails and flavors): the last column sorts each guard by setting. **Net** = a silent safety net, on by default under both Custodia and Libertas, switchable in Settings only under Libertas (the switches live in `/etc/invictus/nets`, 1.6). **Friction** = Custodia only; Libertas has none of it. **Always** = neither a net nor friction, present under both and not switchable (plain words, the record, the remote-help consent design). The sort is clean except G5, which is two things and is split into G5a (net) and G5b (friction) below; nothing in the list argues for a middle setting.

| # | Guard | How | Kind | Setting |
|---|---|---|---|---|
| G1 | Every password prompt says exactly what will change | One Invictus polkit agent (Quickshell `Services.Polkit`, Venus 4.2; `hyprpolkitagent` is the fallback), the same component in both flavors: Atrium runs it inside its shell, Tessera as its own layer-shell process started by autostart. Revised (Alex, 2026-09-30, guard rails and flavors): it reads `/etc/invictus/guardrails` on every prompt, so the flavor never decides what a prompt says. The agent receives the action id, the vendor message and the details dictionary (`BeginAuthentication`, verified in the polkit agent interface). A table in `invictus-guardrails` maps known action ids to plain words with the argument: `org.invictus.sys.install` becomes "Type your password to install Spotify on this computer. Undo: Settings > Updates > Put things back."; `org.freedesktop.Flatpak.app-install` becomes "... to install X for everyone who uses this computer"; `org.freedesktop.udisks2.modify-device-system` becomes "... to change or erase the disk 'Samsung SSD'". Unknown ids show "An app wants to change this computer" plus the vendor message, with the id under Details. `sudo` in a terminal shows the lecture in G3. | Clarity | Always (design A2) |
| G2 | A snapshot before any admin action, so it can be undone | `pam_exec.so` in the `auth` stacks of `/etc/pam.d/sudo` and `/etc/pam.d/polkit-1`, after the password check succeeds, runs `/usr/lib/invictus/pre-admin-snapshot` as root (pam_exec, verified: runs a command per module type, `PAM_SERVICE` and `PAM_USER` in the environment). It makes a snapper snapshot of `@` described "Before: <service>, <user>", important=yes, unless one under 10 minutes old exists. The Atrium polkit dialog shows the same last sentence on every admin prompt, and the terminal shows it once on first open. | Friction, clarity | Friction |
| G4 | Removing the desktop or core packages pauses | `pacman.conf`: `HoldPkg = invictus-base invictus-desktop invictus-guardrails linux linux-lts systemd limine` ("pacman will ask for confirmation before proceeding", verified in pacman.conf(5); with `--noconfirm` the default answer is no, so a pasted one-liner stops). | G5b | Disabling updates or snapshots is possible, not accidental | Settings > Updates offers "Pause updates" for up to 14 days with the plain warning; there is no permanent off switch on screen and the nets in Settings show as on with "Custodia keeps these on" and no switch. Snapshots: no switch on screen at all; the terminal can edit snapper's config. | Friction, clarity | Friction |
| G6 | Erasing a disk pauses | The polkit ids `org.freedesktop.udisks2.modify-device-system` and `-other-seat` (the Disks app's format and partition path; `modify-device` for a removable stick is `yes` for active sessions by default, so a USB stick can still be formatted freely), `org.invictus.sys.guardrails-libertas` and `org.invictus.sys.update-pause` are on the agent's **hold list**: the password field stays disabled for 5 seconds while the warning and the scam line are read, and the dialog says what is on the disk ("Windows 11 and 212 GB of files"). | G9 | Boot always has a way back | The boot guard (2.4) and the snapshot menu in limine. | Safeguard | Net |
| G10 | Everything admin is on the record | Acta (design A11) plus: every pre-admin snapshot with its PAM service and user; every help session with its unlock time; the administrator terminal transcript (5.2). Settings > Help > "What changed" shows it in plain words, and "Put things back" (`rollback <id>`) is one password away. | Clarity, safeguard (undo) | Always |

What stays un-childproofed, on purpose: `sudo` itself, editing any file as root, `systemctl mask`, `dd` and `mkfs` from the terminal, a full-disk erase from a live USB. These are the person's rights (DS1). Each is preceded by a snapshot (G2) except the live USB, and all leave a record (G10).

### 1.6 Switching guard rails live

Revised (Alex, 2026-09-30, guard rails and flavors): new section. Moneta's proposal (password and one warning to Libertas, instant to Custodia, no reboot or logout) checked and refined here.

**One file, every guard reads it.** `/etc/invictus/guardrails` holds one word, `custodia` or `libertas`, root-owned 0644, written only by `invictus-sys guardrails set` with a temp file and `rename(2)`, so no reader ever sees a half state. Every guard is installed on every machine (package `invictus-guardrails`, 6.1) and either reads the file at the moment it acts, or is one of four derived files that the verb rewrites in the same call (`guardrails apply`, idempotent, also run by the installer and by the package's post-install hook). Nothing is installed or removed at switch time, so the switch cannot half-fail on a package download.

| Guard | Custodia | Libertas | What the switch does live | In force |
|---|---|---|---|---|
| G1 plain-words prompts | Message table | Message table (plain words are design A2, not a rail; the scam line and the hold below are the rails) | Nothing; the agent reads the file per prompt | Next prompt |
| G2 pre-admin snapshot (net) | `pam_exec` runs `pre-admin-snapshot` after a successful password in `sudo` and `polkit-1`; always on | The same, on by default; Settings > Safety copies can turn it off, which writes `pre-admin-snapshot = off` to `/etc/invictus/nets`. The `pam_exec` line never moves; the script reads `guardrails` and `nets` and exits 0 when off | Nothing to the PAM files. To Custodia: every net is forced on (the readers ignore `nets` under Custodia), `rm -f /run/sudo/ts/*` (sudoers(5) `timestampdir`, verified) and, in the person's session, `pkcheck --revoke-temp` (verified in pkcheck(1)), so the next admin action of every user really is snapshotted first | Next authentication |
| G3 sudo lecture | `/etc/sudoers.d/40-invictus-guardrails` with `Defaults lecture=always, lecture_file=...` | The drop-in is absent | Derived file 1: written or removed. sudo reads sudoers on every run | Next `sudo` |
| G3 scam line on prompts, terminal first-open card | Shown | Not shown | Nothing; the agent and the terminal launcher read the file | Next prompt or open |

**The nets file.** `/etc/invictus/nets`, root-owned 0644, one `key = on|off` line per net: `pre-admin-snapshot`, `auto-update`, `boot-guard`, `home-snapshots` (the snapshot before an update is snap-pac's and is not switchable: an update without one has no undo, and `update-undo` from the cache depends on it). A missing file or key means on. Written only by `invictus-sys set-config nets.<key> <on|off>` (tier 2 under Custodia, where it is refused anyway; `auth_admin_keep` under Libertas). Every reader checks `guardrails` first: under Custodia the file is ignored and every net is on, so switching to Custodia re-arms all of them in one write and nobody has to remember what was off. Switching back to Libertas restores the person's own choices, which stayed in the file. Turning a net off under Libertas is not on the hold list and has no scam line: Libertas is the person's own choice, made with a password and a hold, once.

**How the switch itself is protected.**

- Two polkit actions, not one, because the two directions need different answers. `org.invictus.sys.guardrails-libertas`: `auth_admin` (no keep), never covered by a `YES` rule, never covered by the help unlock (the `help-unlocked` rule lists the actions it grants and this is not one), on the hold list (G6). `org.invictus.sys.guardrails-custodia`: `YES` for `subject.local && subject.active`, otherwise `auth_admin`. `invictus-sys guardrails set libertas` checks the first, `set custodia` the second; there is no third way to write the file except root in a terminal, which is the person's right (1.4).
- The prompt to Libertas (Clio polishes): "Switch to Libertas? Nothing will pause or warn you before something is erased, and Help will be able to do more on its own. Safety copies stay on unless you turn them off. Type your password if you're sure. If someone on the phone or a website told you to do this, stop and use Ask Support in Help." Password field disabled for 5 seconds. The Settings page offers "For an hour" (default, DS13) and "Until I turn them back on"; the hour is a wall-clock end in `/etc/invictus/guardrails-until`, enforced by a root timer, at boot and by `invictus-sys` itself (12.1), and ends with "Guard rails are back on".
- The snapshot before the switch to Libertas is taken by the verb itself, not only by G2, so it exists even if PAM is misconfigured: "Before: guard rails off".
- The assistant has no tool for either direction (tier 3): the answer is "You can do that yourself in Settings > Guard rails", the same when the person says someone told them to.
- `invictus-sys guardrails set` refuses any word other than `custodia` and `libertas`, and refuses to run while `guardrails apply` holds its lock, so two switches cannot interleave.

**Mid-session.**

- *An admin prompt already open* (a polkit dialog waiting for a password): polkitd decided that check under the rules in force when it began, and the answer stands; G2's snapshot happens if `guardrails` says `custodia`, or `nets` says on, at the moment the password is checked. The one-second window where a prompt opened under Custodia is answered under Libertas is accepted and stated; the switch to Libertas always comes with its own snapshot, so nothing in that window is unrecoverable.
- *A running help session*: the session, the banner, the whitelist and the assistant pause (TS7) do not depend on the rails and continue. Switching to Libertas needs the person's password at their own keyboard, which Alex's remote input cannot type (5.2 step 4), and the help unlock does not cover the action, so Alex cannot switch the rails off from the session. Switching to Custodia during a session is instant and leaves the unlock in place until it ends; the unlock is scoped to the session, not to the rails.
- *The assistant*: a tool call in flight when the panel receives the signal is killed with the process; `invictus-sys` verbs are atomic at their own level (a package transaction completes or is rolled back by pacman, not left half-done), and the person sees "Moneta is starting again with the new rules". To Libertas, a `claude` that keeps running because the panel is not running (a terminal `claude`) already has no Bash tool and cannot gain one without a restart, which the managed file now allows; that is the person's own choice on their own machine. To Custodia, the kill matters: SM21 proves no assistant process with a Bash tool survives the switch by more than 5 seconds.
- *Cached credentials*: to Custodia, sudo timestamps and polkit temporary authorizations are cleared (G2 row) so "snapshot before every admin action" is true from the first one. To Libertas nothing is cleared.
- *Auto-update in progress*: `invictus-update --auto` holds a lock; `guardrails set` waits for it (up to the transaction's end) before rewriting the pacman include, and says "Finishing an update first" if that takes more than a few seconds.

**Does Alex's direction create a new risk?** Two, both contained. TS11: a Settings switch that turns the rails off is a new target for the phone scam; contained by making it the most guarded action on the machine, by the hour default (DS13), by the pre-switch snapshot, and by the doctor and the helper digest reporting "Libertas since <time>". TS12: an instant switch to Custodia is a privilege change with no password; contained because the only privilege Custodia grants without a prompt is the tier 1 list, which by MUST SM22 must never contain anything a user-level process could turn to harm, and because the instant direction is local-session only and logged. A third is not a risk but a trap avoided: had the rails been tied to the flavor, a friend clicking "Tessera" in Desktop style would have silently lost their snapshots; keying on one file that the flavor never touches (SM23) removes it.

## 2. Updates with no human decision

Unchanged from the first draft except 2.6, which is new after DS1.

### 2.1 What runs

`invictus-update --auto`, a root service on a timer (`invictus-auto-update.timer`, hourly, `RandomizedDelaySec=15min`, `Persistent=true`), which does nothing unless every gate in 2.2 is open, then:

1. Refresh keyrings first: `pacman -Syu --needed archlinux-keyring invictus-keyring` (the standard fix for machines that were off for a long time).
2. Download only: `pacman -Syuw --noconfirm` (all packages fetched before anything changes; `checkupdates` from pacman-contrib for the preview so the live database is never left half-synced).
3. Install: `pacman -Su --noconfirm`. snap-pac makes the pre and post root snapshots (already in the main design). `invictus-update` writes the transaction list (package, old version, new version) to `/var/lib/invictus/update/last.json` and copies the same list to `/boot/invictus/pending` on the ESP with `count = 0` (section 2.4).
4. `invictus-doctor --post-update` (main design 1.4). On failure: `invictus-update --undo`, which reinstalls the previous versions from `/var/cache/pacman/pkg` with `pacman -U --noconfirm` (the cache is on `@pkg`, kept out of snapshots and kept at least two versions deep by `paccache -rk2`), reruns the doctor, and if it is still red, does `limine-snapper-restore` to the pre-update snapshot (Vulcan verifies the non-interactive form; the README documents the command but not its flags) and schedules a restart. Either way a helper request is filed (section 4.4).
5. Flatpak: `flatpak update --user -y --noninteractive` as the person (user timer `invictus-flatpak-update.timer`), with the list of apps whose permissions grew written to the helper digest (the Arch wiki warns unattended Flatpak updates can add permissions; in Custodia an old browser is the bigger risk, so we update and report).
6. Result: a Desk card in plain words, never a question. In Atrium, where the Desk is not shown, the result is the update message from Venus's `simple-mode.md` 4.2 (`Your computer is up to date` or `Updates are ready`). Kernel, `mesa`, `systemd`, the hypr* set or `sddm` in the list set `restart-needed`.

Nothing ever asks the person a question. `.pacnew` files are the helper's, listed in the digest. Manual-intervention updates (the ones Arch announces on its news page) are why the stable channel exists: Alex's testing week is the human decision, once, for everyone.

### 2.3 Restarts

A restart is only needed for the packages in 2.1 step 6. The card says so. Automatic restart happens at the first moment all of these hold: `restart-needed` set, between 02:00 and 06:00 local, on mains, no session active or idle over 30 minutes, no help session, not in a game. If the person shuts down or restarts themselves first, that clears it. Laptops on battery wait. Owner decision DS2 (night restart) because someone might leave a render or a download running overnight; the recommendation is Approve, since the idle and game gates cover the common cases and the alternative is running an old kernel for weeks.

### 2.4 The boot guard (automatic rollback)

Facts, verified 2026-09-30: limine's `CONFIG.md` has no boot counting, but on UEFI limine honours the Boot Loader Interface's `LoaderEntryOneShot` EFI variable ("takes precedence over `default_entry`"). `systemd-bless-boot` counts only for systemd-boot style entries (`LoaderBootCountPath`). limine-snapper-sync creates the snapshot entries and offers `limine-snapper-restore`, and nothing automatic. So the guard is ours, small, and lives in two places:

1. `invictus-boot-guard` mkinitcpio hook (runs in the initramfs, before the root is mounted): mount the ESP read-write, and if `/boot/invictus/pending` exists and the kernel command line does not carry a snapshot root (`rootflags=subvol=@/.snapshots/...`, which is how limine-snapper-sync boots a snapshot), increment `count`. If `count` is now 3 (two full boots since the update did not reach "good"), write `LoaderEntryOneShot` for the pre-update snapshot entry (the entry name limine-snapper-sync generated for the snapshot id in `pending`; Vulcan takes the exact form from the generated `limine.conf`), set `rolled-back = <snapshot id>` in `pending`, and reboot. Nothing else happens in the initramfs.
2. `invictus-boot-guard.service` (root, after `graphical.target`): waits up to 5 minutes for "good", which is `display-manager.service` active without a restart for 90 seconds, plus, if a user logs in inside the window, the `invictus-session` user service's `session-ok` file (Hyprland answered `hyprctl version`). On good: delete `pending`, mark the post-update snapshot as "last good" (`snapper modify --cleanup-algorithm "" <id>` on that one and release the previous "last good"), write to Acta. On timeout: reboot (the counter does the rest).
3. When a boot lands in a snapshot (root is a `.snapshots` subvolume) and `pending.rolled-back` is set: `invictus-boot-guard.service` runs `limine-snapper-restore` to that snapshot non-interactively, clears `pending`, files a helper request ("Update on <machine> rolled back; the machine is on the snapshot from <date>"), sets `hold-updates` until the helper clears it, and reboots into the restored system. Auto-updates stay held so the same update is not retried the next hour. The helper request here is a `report` entry of `design-inbox.md` (section 2), and the message may end with "Support has been told" only once that design's state is `sent` (I6).

Limits, stated plainly: a kernel that fails before the initramfs runs (a broken kernel image) cannot count itself. The LTS kernel is the second menu entry and the pre-update snapshot the third; the helper talks them through pressing a key at boot, or visits. Every other failure (GPU driver, systemd, SDDM, Hyprland, a bad config) reaches the counter. Worst case before the machine fixes itself: two boots of up to 5 minutes each, then one more boot. Fallback if the hook proves fragile on hardware (Phase 3 risk R1 applies): Custodia machines move to systemd-boot with its native counting (`bootctl`, `systemd-bless-boot`) and lose the snapshot menu in the bootloader; the snapshots and `snapper rollback` still exist. That is a config change to the installer job, not a redesign.

### 2.5 Snapshots on a Custodia machine

As the main design (snap-pac, `NUMBER_LIMIT=10`, no timeline on `@`), plus: "last good" is exempt from cleanup, the pre-admin snapshots of G2 are `important=yes` with `NUMBER_LIMIT_IMPORTANT=10`, `@home` gets a timeline config if DS12 is approved (`TIMELINE_LIMIT_HOURLY=24`, `TIMELINE_LIMIT_DAILY=7`, nothing longer), and `@pkg` keeps two versions of every package so `--undo` works offline. The "Undo last update" button calls `invictus-sys update-undo`, pre-authorised for the person (section 4.2) because it only moves between two states the machine has already been in.

### 2.6 Pausing updates

Revised after DS1 (Alex, 2026-09-30): new.

Settings > Updates has "Pause updates" with 1, 7 or 14 days, through `invictus-sys update-pause <days>` (password, on the hold list of G6, so the warning reads: "Updates keep this computer safe. Paused updates start again by themselves on <date>."). It writes `/etc/invictus/update-pause` with an expiry; the gate in 2.2 reads it; the doctor and the helper digest show it. There is no "off" on screen (G5).

## 3. Installing apps without a terminal

### 3.1 The path

Per-user Flatpak from Flathub. Verified against the Flatpak docs and the Arch wiki: `--user` installs need no privilege at all (the polkit actions `org.freedesktop.Flatpak.app-install` and friends, `auth_admin_keep` by default, only guard system-wide installs through the system helper). The remote is added per user at first login: `flatpak remote-add --user --if-not-exists flathub https://dl.flathub.org/repo/flathub.flatpakrepo` and `flatpak remote-modify --user --subset=verified flathub` (the verified subset: apps published by their own developers).

Store: Bazaar (`extra`, 0.9.4, "a fast and modern store for GNOME with focus on Flatpaks, particularly from Flathub"), because it is Flathub-only and has no pacman plugin, so it cannot become a system package manager by accident. Vulcan verifies that Bazaar defaults to the user installation (unverified today); if not, `gnome-software` with only the Flatpak plugin is the fallback. Flatseal (`extra`, 2.4.1) is installed, in All apps, not pinned.

Curated default set, preinstalled at first login as user Flatpaks (owner decision DS5 for the list; a starting proposal): LibreOffice, VLC, Spotify, Signal, Zoom, Thunderbird. Browser, Discord and Steam are native packages already in the metas. The assistant's `app_install` tool takes an app name, resolves it against the verified subset first and installs per user with no password; an app outside the subset is offered with its permissions in plain words and needs the person's password (tier 2, 4.2); an app not on Flathub at all is a helper request with the name ("Alex will check this one first").

Revised after DS1 (Alex, 2026-09-30): the subset is a default, not a wall. Native packages from our repos are one password away through `invictus-sys install` (tier 2), and a system-wide Flatpak install, if the person ever asks for one, gets the plain-words prompt of G1.

### 3.2 What it means for security

- The sandbox is whatever the app's manifest says. The Arch wiki's warning stands: many Flathub apps have `filesystem=home` or `--socket=x11`, so "sandboxed" is not "safe". The verified subset removes the anonymous-repackager risk, not the permission risk. Bazaar and the assistant show the app's reach in plain words before installing ("This app can see all your files", from `flatpak info --show-permissions`); the person will still say yes, so the digest to the helper lists every install with its permissions and the helper can remove or override (`flatpak override --user`) remotely.
- A per-user Flatpak cannot touch `/usr`, `/etc`, the bootloader or another user. Nothing in Flatpak escalates to root, and the machine's own updater does not read `~/.local/share/flatpak`.
- No system-wide Flatpak installation is configured by default, so nothing asks for a password in the ordinary path. AUR stays out (design MUST A3).

### 4.5 Plain words, and never a command

The plugin's Custodia persona (Clio writes it; the rule is here): no commands, no paths, no package names, no "open a terminal", no "run", no "sudo". If the person asks for something the tools cannot do, the answer is "I'll ask Support to do that" plus `helper_ask`, or a Settings path, never instructions to type. ### 5.2 How a session goes

Revised after DS1 (Alex, 2026-09-30): steps 1 and 4.

1. The person presses "Get help". Entry points: the Help panel's `Let Support see my screen` button (proposed to Venus for the open M3 item, since Atrium has no Desk and no Super+H), or asking Moneta. That runs `invictus-sys help start` (tier 1): starts `rustdesk.service` (not enabled at boot), opens the RustDesk window, and shows the helper's contact card (`helper_person`, `helper_contact` and the RustDesk ID, all from `/etc/invictus/helper.conf`, `design-inbox.md` 3.5; the shipped card reads `Sol Invictus support · solinvictus.support@gmail.com`) in big digits so they can read it out or send it. A 30-minute timer stops the service if no session starts.
2. Alex connects from his RustDesk with his own ID. The person's client has `approve-mode=click` (manual accept only, no password mode at all), `id-whitelist=<Alex's RustDesk ID>` (any other ID is refused before a dialog appears), `allow-only-conn-window-open=Y` (closing the window ends everything). They click Accept.
3. While connected: a banner at the top of every monitor, `Support is using your computer` with a `Stop` button (Venus's wording, `simple-mode.md` 4.2), `/run/invictus/help-session` exists (the updater's gate, and the assistant's pause), and Acta logs "help session started by <person>, peer <id>".
4. Admin work, the **help unlock**. The banner has a second button, `Let Support make changes`. It runs `invictus-sys help unlock`, whose polkit action `org.invictus.help.unlock` is `auth_self` (the person's own password, never cached, not covered by any YES rule), drawn by the Atrium agent as: "Type your password to let Support change settings on this computer for the next hour. You can press Stop at any time." The person types it at their own keyboard (RustDesk carries the screen out and Alex's input in; local keystrokes are not sent to the controller). `invictus-sys` then writes `/run/invictus/help-unlock` (uid, help session id, expiry = now + 60 min), takes a G2 snapshot described "Before: help session <id>", and the banner reads `Support can change settings until 15:40 · Stop`. The polkit rule grants, for the person's user, `polkit.Result.YES` on `org.invictus.sys.*` (except `org.invictus.sys.guardrails-libertas`, `org.invictus.sys.assistant-full-access`, `org.invictus.sys.ai-on` and `org.invictus.help.unlock`; revised for guard rails, Settings and No AI, 2026-09-30) and on `org.invictus.help.shell` while `polkit.spawn(["/usr/lib/invictus/help-unlocked", subject.user])` succeeds (polkit rules may spawn a checker; verified in polkit(8)). `org.invictus.help.shell` opens an administrator terminal (`pkexec` to root) whose whole transcript is recorded with `script` to `/var/log/invictus/help/<session id>.log`, readable by the person in Settings > Help > "What changed". Everything Alex does through `invictus-sys` is logged `by <person>, help session <id>, unlocked`. Other polkit prompts (a system Flatpak, a disk) stay password prompts: Alex asks the person to type, or uses the terminal. The unlock ends with the session, at expiry, or on Stop; renewing it is the same password prompt again. Owner decision DS10.
5. End: the person presses Stop or closes the window, or Alex disconnects, or 10 minutes of inactivity pass (`allow-auto-disconnect=Y`, `auto-disconnect-timeout=10`). `invictus-sys help stop` stops the service, removes the session and unlock files, and closes the administrator terminal. Acta logs the end.

Server: the RustDesk public rendezvous servers in v1 (traffic is end-to-end encrypted; the servers see IDs and relay bytes they cannot read), with Alex's own `hbbs`/`hbbr` as owner decision DS7 later. The friend-side settings above are written by `invictus-guardrails` at install; RustDesk reads its own config, and `allow-remote-config-modification=N` stops Alex's side from changing them mid-session. Whether the file can be made root-owned so the person's clicks in RustDesk's own settings cannot loosen it is unverified; if not, `invictus-session` re-asserts the settings every time the service starts. Revised after DS1 (Alex, 2026-09-30): the person is admin and may loosen anything; the re-assert protects against a stray click, not against them.

### 5.3 What must never happen silently

- No unattended access: no permanent password, no "password" or "password-click" approve mode, no autostarted RustDesk service, no sshd, no Tailscale on a Custodia machine. Revised after DS1 (Alex, 2026-09-30): and no standing helper account unless DS9 is approved and the person opted in.
- No hidden channels: `enable-file-transfer=N`, `enable-terminal=N` (RustDesk's own terminal feature bypasses the screen), `enable-tunnel=N`, `enable-record-session=N`, `enable-lan-discovery=N`, `direct-server=N`, `enable-remote-printer=N`, `enable-camera=N`. Files move by the person seeing it happen on screen.
- No admin work outside a session: the help unlock exists only while `/run/invictus/help-session` does, and its file dies with it.
- No session without the banner. If the banner process dies, `invictus-session` ends the RustDesk session.

## 12. Settings answers (Minerva, 2026-09-30 evening)

Answers to Venus's four questions in `settings.md` section 9, plus the loose ends they uncovered. Where an answer changes her design, `settings.md` carries the change with a pointer here. New MUSTs are SM25 and SM26; SM15, SM17 and SM21 are revised (12.5).

### 12.1 Timed Libertas: the until-file

**Stored.** `/etc/invictus/guardrails-until`, root-owned 0644, three `key = value` lines: `until = <RFC3339 with offset>`, `since = <RFC3339>`, `by = <user>`. Written by `invictus-sys guardrails set libertas --for <duration>` with a temp file and `rename(2)`, **before** the `guardrails` file is written (a crash between the two leaves an until-file next to `custodia`, which every reader ignores and `apply` removes; the other order could leave an untimed Libertas). Removed by every path that writes `custodia` and by `set libertas` without `--for`. Absent while `guardrails` reads `libertas` means "until I turn them back on". Readers (Settings, the Atrium taskbar, waybar, the Help panel, the doctor, the helper digest, the polkit agent's prompt text) watch it with inotify and never compute an end themselves.

**Enforced, in three places, all from the file and never from "now plus an hour", so a restart cannot extend it:**

1. A transient root timer, armed by the verb: `systemd-run --unit invictus-guardrails-expiry --on-calendar=<until> --timer-property=AccuracySec=1s /usr/lib/invictus/guardrails expire`. Reused, not new: no daemon, a wall-clock calendar timer, which fires on resume if the end passed during suspend. `guardrails expire` runs as root, re-reads the file, and if `now >= until` performs the Custodia switch through the same code as `set custodia` (derived files, cached credentials cleared, the Moneta restart, Full access cleared per 12.3), with how = `expired` in the Acta line and the notice `Guard rails are back on`; if the clock now says the end is still ahead (the clock was moved), it re-arms and exits.
2. At boot: `invictus-guardrails.service`, a static root oneshot, `Before=display-manager.service`, runs `guardrails apply`, which now also reads the until-file: end passed, switch to Custodia before anyone can log in, Acta `guard rails: libertas -> custodia, expired 15:20 while the computer was off, applied 18:02`, and `/run/invictus/guardrails-notice` so `invictus-session` shows `Guard rails are back on` at the first login and deletes it; end ahead, re-arm the transient timer (transient units do not survive a reboot, which is why this step exists). So a machine off at 15:20 comes back as Custodia, as Venus assumed.
3. The root side of `invictus-sys`, before it reads the tier for any verb: `libertas` with a passed `until` is treated as Custodia and `expire` is run first. This keeps the countdown honest if the timer unit is ever missing (someone stopped it, a crash), at the cost of one file read per verb.

**Edge cases.** Re-running `set libertas --for` during a timed Libertas replaces the end, and `set libertas` without `--for` removes it; both go through the full guarded prompt (`guardrails-libertas`, hold, scam cue, password), so "extend by another hour" costs the same as the first hour. Changing the system clock moves the end with it; that is root's right (1.4) and lands in Acta like any other admin action. The expiry mid-session behaves exactly as `set custodia` in 1.6 (a running help session continues, an open admin prompt is answered under the old rules, the assistant restarts). Whether systemd re-evaluates a calendar timer on a clock change is expected (it does for `OnCalendar`) and Vulcan verifies it in SM25.

### 12.2 Putting all your files back

**Recommendation: `Look inside` only in v1.** Not a tier 1 verb, not a logout job yet. Reasons:

- A whole-home revert is the one action on the Safety copies page that can silently remove hours of work from every app at once: downloads, documents, browser sign-ins, Moneta's own sign-in (`~/.claude`), Settings' per-user files, the flavor file. "A copy of now is made first" only helps a person who can find their way back through Look inside, which is the loop this audience will not follow.
- It cannot run cleanly while the person is logged in: the session lives in `@home`, apps hold files open, and a swap only takes effect at the next login anyway. So the honest version is a logout job, which needs a root hook at session end, a per-user restore (`@home` holds every user; a subvolume swap would revert them all), and its own pen test.
- `Look inside` covers the case the page is for ("put my photo back") with no way to lose anything.

**What to fix now, so the logout job (v1.1) is possible later without a reinstall:** the DS12 snapper config `home` keeps its `.snapshots` on its own subvolume, `@home-snapshots`, mounted at `/home/.snapshots` (as `@snapshots` is for `/`, `design.md` 3.2), so a later restore never snapshots the snapshots; `ALLOW_GROUPS = users` with `SYNC_ACL = yes` so the person can traverse `/home/.snapshots/<n>/snapshot/` (each user's directory inside keeps its own 700, so nobody sees another person's files); snapshots are read-only, as snapper makes them. `Look inside` opens `/home/.snapshots/<n>/snapshot/<user>/` in Files, read-only. SM17 is revised for the path.
